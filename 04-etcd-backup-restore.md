# etcd: Backup and Restore

etcd is the key-value store that holds **all** Kubernetes cluster state — every object (pods, services, secrets, configmaps) lives here. If etcd is lost and there's no backup, the cluster is unrecoverable. Backup/restore is a core CKA exam topic.

---

## Prerequisites: Installing etcd Tools

Two separate tools are needed:

| Tool | Purpose | How to get |
|------|---------|------------|
| `etcdctl` | CLI client for interacting with a running etcd (queries, backups) | `sudo apt install etcd-client` |
| `etcdutl` | Offline utility for snapshot inspection and restore (works on files, not a live server) | Manual download from [etcd releases](https://github.com/etcd-io/etcd/releases) |

On Ubuntu 22.04, `etcdutl` is not packaged with `etcd-client` — it must be downloaded separately from the GitHub releases page.

**Why two tools?** `etcdctl` talks to a running etcd server over the network. `etcdutl` operates on local snapshot files without needing a running server — critical for restore scenarios where etcd is stopped.

---

## Connecting to etcd

Enter the control plane node:

```bash
multipass shell k8s-cp1
sudo -i
```

Every `etcdctl` command requires three things:

1. **API version** — `ETCDCTL_API=3` (defaults to legacy v2 which uses a different data model)
2. **Endpoint** — where etcd listens for client connections (`localhost:2379` on the control plane)
3. **TLS certificates** — etcd requires mutual TLS; all comms are encrypted and authenticated

The certificates are generated by `kubeadm init` and stored in `/etc/kubernetes/pki/etcd/`:

| File | Purpose |
|------|---------|
| `ca.crt` | Certificate Authority — verifies the server's identity |
| `server.crt` | Server certificate — presented by etcd |
| `server.key` | Server private key — proves ownership of the cert |

### Example: List cluster members

```bash
ETCDCTL_API=3 etcdctl --endpoints localhost:2379 \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  member list
```

Output:

```
31cafa10d5722363, started, k8s-cp1, https://192.168.252.2:2380, https://192.168.252.2:2379
```

The output format is: **ID, status, hostname, Peer URL, Client URL**

- **Peer URL** (port 2380) — etcd-to-etcd communication between control plane nodes (cluster consensus)
- **Client URL** (port 2379) — where clients (like kube-apiserver) connect to read/write data

In a multi-CP cluster you'd see one line per control plane node.

## Creating Backups

```bash
ETCDCTL_API=3 etcdctl --endpoints localhost:2379 \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  snapshot save snapshot.db
```

This exports the entire etcd database into `snapshot.db` in your current directory. The snapshot is a point-in-time copy — any changes made after this command won't be in the backup.

**What's in the snapshot?** Every Kubernetes object: pods, deployments, services, secrets, configmaps, RBAC rules, custom resources — everything the API server stores. It does NOT include:
- Container images (those are in the registry)
- Data inside persistent volumes (those are on the storage backend)
- Node-local state (kubelet configs, container runtime state)

---

## Verifying Backups

Use `etcdutl` (not `etcdctl`) to inspect the snapshot file offline:

```bash
etcdutl --write-out=table snapshot status snapshot.db
```

Output:

```
┌──────────┬──────────┬────────────┬────────────┬─────────┐
│   HASH   │ REVISION │ TOTAL KEYS │ TOTAL SIZE │ VERSION │
├──────────┼──────────┼────────────┼────────────┼─────────┤
│ 1e6e702c │   259844 │        509 │      10 MB │   3.6.0 │
└──────────┴──────────┴────────────┴────────────┴─────────┘
```

| Field | Meaning |
|-------|---------|
| HASH | Integrity checksum — detects corruption |
| REVISION | etcd's internal transaction counter (like a database sequence) |
| TOTAL KEYS | Number of key-value pairs stored |
| TOTAL SIZE | On-disk size of the snapshot |
| VERSION | etcd version that created the snapshot |

If this command errors or shows a bad hash, the snapshot is corrupt — don't restore from it.

## Restoring Backups

This is a **disruptive process** — the entire control plane goes down during restore. In production this means no API access until etcd is back.

### Pre-restore: Verify the snapshot is healthy

```bash
etcdutl --write-out=table snapshot status snapshot.db
```

### Step 1: Stop etcd

Kubernetes runs etcd as a **static pod** — the kubelet watches `/etc/kubernetes/manifests/` and runs whatever YAML it finds there. Moving the manifest out stops etcd:

```bash
sudo mv /etc/kubernetes/manifests/etcd.yaml /tmp/etcd.yaml
```

Verify etcd is actually stopped:

```bash
sudo ctr -n k8s.io tasks list | grep etcd
```

Should return empty. (`ctr` is the containerd CLI; `-n k8s.io` is the namespace where Kubernetes containers run.)

**Why not just `kubectl delete`?** Because kubectl talks to the API server, which talks to etcd — if etcd is broken, kubectl won't work. Static pod manipulation bypasses the entire API chain.

### Step 2: Move old data aside

```bash
sudo mv /var/lib/etcd /var/lib/etcd.bak-$(date +%s)
```

We rename rather than delete — if the restore fails, the old data is still available.

### Step 3: Restore the snapshot

```bash
sudo etcdutl snapshot restore snapshot.db \
  --name k8s-cp1 \
  --initial-cluster k8s-cp1=https://192.168.252.2:2380 \
  --initial-cluster-token etcd-restore-$(date +%s) \
  --initial-advertise-peer-urls https://192.168.252.2:2380 \
  --data-dir /var/lib/etcd
```

**What each flag does:**

| Flag | Purpose |
|------|---------|
| `--name` | This node's etcd member name (must match what's in the cluster) |
| `--initial-cluster` | All etcd members in format `name=peerURL`. Comma-separated for multi-CP |
| `--initial-cluster-token` | Unique token to prevent restored nodes from accidentally joining the old cluster |
| `--initial-advertise-peer-urls` | This node's peer URL for cluster communication |
| `--data-dir` | Where to write the restored data (must match etcd's configured data directory) |

**For multi-CP clusters**, `--initial-cluster` lists all control plane nodes:

```bash
--initial-cluster k8s-cp1=https://192.168.252.2:2380,k8s-cp2=https://192.168.252.3:2380
```

Each node must also run the restore with its own `--name` and `--initial-advertise-peer-urls`.

Look for this line in the output to confirm success:

```
info    snapshot/v3_snapshot.go:334     restored snapshot
```

### Step 4: Restart etcd

Move the manifest back so kubelet picks it up:

```bash
sudo mv /tmp/etcd.yaml /etc/kubernetes/manifests/etcd.yaml
```

Give it a minute or two for etcd to start and the API server to reconnect.

### Step 5: Verify health

Check etcd endpoint health:

```bash
ETCDCTL_API=3 etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  --endpoints=https://192.168.252.2:2379 \
  endpoint health
```

If healthy, verify the cluster itself:

```
$ kubectl get nodes
NAME          STATUS   ROLES           AGE   VERSION
k8s-cp1       Ready    control-plane   35h   v1.36.3
k8s-worker1   Ready    <none>          35h   v1.36.3
k8s-worker2   Ready    <none>          35h   v1.36.3
```

All nodes showing `Ready` means etcd is back, the API server is reading from it, and the cluster is healthy.

## Quick Reference: Backup/Restore Cheatsheet

```bash
# Backup
ETCDCTL_API=3 etcdctl snapshot save /path/to/backup.db \
  --endpoints localhost:2379 \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt

# Verify
etcdutl --write-out=table snapshot status /path/to/backup.db

# Restore (stop etcd first!)
etcdutl snapshot restore /path/to/backup.db \
  --data-dir /var/lib/etcd \
  --name <node-name> \
  --initial-cluster <name>=<peer-url> \
  --initial-cluster-token etcd-restore-<unique> \
  --initial-advertise-peer-urls <this-node-peer-url>
```
